## 1. Архитектура и распределение задач (FreeRTOS)

### 1.1 Проектная топология

- **Core 0 — супервизор:** `loop()`, Wi-Fi TCP, USB-UART, FSM, приём и буферизация УП, телеметрия.
- **Core 1 — движение:** высокоприоритетная задача `motionTask` (DDA/Брезенхем) и аппаратный таймер шагов.
- Обмен кадрами — через структуру `nextSeg` и кольцевой буфер тактов `stepRingBuffer`.

### 1.2 Сейчас: фактическое распределение

- `loopTask` Arduino (`ARDUINO_RUNNING_CORE = 1`, приоритет 1) — на **Core 1**;
- `motionTask` (`xTaskCreatePinnedToCore`, приоритет 24, стек 8192) — на **Core 1**;
- таймерный ISR создан из `setup()`, то есть тоже на **Core 1**;
- стек Wi-Fi/lwIP IDF живёт на Core 0, но **вся обработка команд и сети** (`loop`) — на Core 1 и конкурирует с генератором шагов.

> **⚠ Отличие:** «межъядерный» обмен `nextSeg` фактически происходит внутри одного ядра. Прежнее описание «Core 0 — супервизор» не соответствует коду.
> **Проект:** движение должно быть изолировано на отдельном ядре, вся остальная логика — на другом. Это остаётся целью (TODO).

## 2. Геометрия, кинематика и механика

Конструкция рассчитана на жёсткую обработку протяжённых деталей (до 4 м) и собрана на пространственной сварной ферме.

- **Ось X (4000 мм, ведущая):** рейка—шестерня, `stepsPerMmX = 100.0`. Высокие скорости холостого хода, отсутствие провиса длинного ШВП. По X перемещается тяжёлая чугунная каретка со шкафом автоматики, поэтому ускорение ограничено (`maxAcceleration = 150.0 мм/с²`).
- **Оси Y (500 мм) и Z (200 мм):** направляющие «ласточкин хвост», трапецеидальные винты, `stepsPerMmY/Z = 400.0`. Механический поджим пружинами для выборки люфта. Из-за высокого трения покоя стартовая скорость вектора задана повышенной (`minVectorSpeed = 2.0 мм/с`), чтобы драйверы не уходили в Alarm.
- **Кареточное размещение шкафа:** драйверы, ESP32, датчики и БП закреплены на подвижной каретке. Сигнальные линии STEP/DIR, UART2 к ESP32-CAM и датчики короткие (<1 м) и неподвижны относительно шкафа; в кабель-треке — только сетевой кабель питания класса High-Flex.

Диапазоны `minX…maxZ` в конфиге присутствуют, но **программно не проверяются** (см. раздел 11).

## 3. Конечный автомат (FSM) и безопасность

### 3.1 Состояния

| Состояние | Назначение |
|---|---|
| `STATE_INIT` | начальное состояние после подачи питания (кратковременное) |
| `STATE_ALARM` | авария: моторы обесточены, реле шпинделя/СОЖ выключены |
| `STATE_IDLE` | покой, приём команд; при `!isHomed` отображается как `IDLE (LOCKED)` |
| `STATE_JOGGING` | ручное перемещение |
| `STATE_CALIBRATION` | сервисные сканирования (`START_CALIBRATION`, `SCAN_GEOMETRY`) |
| `STATE_MAP_TRANSFER` | импорт карты лазера с ПК |
| `STATE_RUNNING` | выполнение УП |
| `STATE_HOMING` | поиск баз |
| `STATE_HOLD` | технологическая пауза |
| `STATE_GCODE_UPLOAD` | приём бинарных кадров УП |

### 3.2 Переходы и блокировки

- `changeState()` возвращает `bool`: `false` — переход запрещён (`ALARM` или нет хоуминга). В этом случае выдаётся `ERROR: ...`, а вызывающий обработчик обязан не начинать движение.
- При `!isHomed` запрещены `RUNNING`, `JOGGING` и `CALIBRATION`; исключение — `JOGGING` при `allowJogBeforeHoming = true` (по умолчанию **true**).
- `RESET_ALARM` **сбрасывает** `isHomed = false`, то есть после сброса аварии требуется повторный хоуминг.
- `ESTOP` переводит в `ALARM`, обесточивает моторы и выключает реле.
- `HOME`/`$H` доступны только из `IDLE`.
- `HOLD`/`!` — только из `RUNNING`/`JOGGING`; `RESUME`/`~` — только из `HOLD`.

`HOME`, `JOG`, `START_PROGRAM`, `START_FROM_LINE`, `START_CALIBRATION` и `SCAN_GEOMETRY` проверяют результат `changeState()` и при отказе не двигают станок. `startProgramExecution()` дополнительно требует `isHomed`, `totalLoadedCommands > 0` и отсутствие `ALARM`.

### 3.3 Аварийные входы

- `ESTOP_PIN` (GPIO 34) — аварийная кнопка, активный уровень **HIGH**.
- `MOTORS_ALARM` (GPIO 35) — последовательное ИЛИ ошибок драйверов, активный **HIGH**.
- `ENDSTOPS_PIN` (GPIO 39) — **единая последовательная NC-цепь** концевиков X/Y/Z, срабатывание = **HIGH**.

Проверки выполняются в двух местах: `checkHardwareSecurity()` в `loop()` и в таймерном ISR.

Аварийная ветка ISR (`emergencyStopFromISR()`) делает только аппаратные действия: обесточивает драйверы, снимает STEP/реле, выбрасывает очередь и выставляет `volatile`-флаги `motionStopRequested` / `alarmRequested`. Ни `changeState()`, ни `Preferences`, ни `Serial`/`String` в прерывании нет. `changeState(STATE_ALARM)` и запись `lastLine` выполняет `checkHardwareSecurity()` в `loop()`, когда увидит `consumeAlarmRequest()`.

`requestMotionStop()` — единая мягкая остановка: кратковременно отключает таймер, в критической секции очищает кольцевой буфер, синхронизирует `plannerSteps* = currentSteps*`, опускает STEP и снова включает таймер. Выдача шагов при этом заблокирована флагом `motionStopRequested`, поэтому ISR продолжает следить за `ESTOP`/`MOTORS_ALARM` даже в `IDLE`. Вызывается из `changeState(ALARM/IDLE)`, команды `STOP` и аварийного выхода из хоуминга. `prepareVectorSegment()` и `armMotionTimer()` заново разрешают выдачу шагов только после этого.

> **⚠** GPIO 34/35/39 — входы без внутренней подтяжки: `INPUT_PULLUP` для них не работает, внешние резисторы/оптроны обязательны.

### 3.4 Хоуминг

Последовательность: **Z → X → Y** (Z уходит вверх первой, чтобы не сломать инструмент).

- скорость фиксированная: `HOMING_DELAY_TICKS = 50` тиков по 10 мкс → 0,5 мс/шаг (2 кГц) → **20 мм/с по X**, **5 мм/с по Y/Z**;
- после срабатывания датчика — пауза 100 мс и отъезд (pull-off): X 400 шагов (4 мм), Y/Z 800 шагов (2 мм);
- направления: `homingDirX = -1`, `homingDirY = -1`, `homingDirZ = +1`;
- по завершении каждой оси `currentSteps*` и `plannerSteps*` обнуляются.

**Защита (P0-5):**

- `armMotionTimer()` взводится перед циклом; если FSM в `ALARM` — хоуминг не начинается;
- в обоих циклах (`поиск` и `pull-off`) проверяются `ESTOP`, `MOTORS_ALARM`, `alarmRequested`, `motionStopRequested` и `currentMachineState == STATE_ALARM`;
- ограничение хода: `(|max−min| + 100 мм) × stepsPerMm` шагов на ось, плюс таймаут по времени; превышение → `ALARM`;
- после pull-off концевик обязан отпуститься (`LOW`); если цепь осталась разомкнутой → `ALARM`;
- `isHomingActive` сбрасывается на **всех** путях выхода, поэтому ISR снова контролирует концевики;
- аварийный/мягкий выход вызывает `requestMotionStop()`; `runFullHoming()` не переводит станок в `IDLE` после `ALARM`.

**Ограничение:** все оси по-прежнему используют один вход GPIO 39, поэтому при уже открытой цепи (например, X стоит на своём концевике) хоуминг следующей оси может завершиться сразу — это P1-6 (раздельные концевики).

### 3.5 Инженерный обход хоуминга

`SET_HOMED_DEBUG` ставит `isHomed = true` без движения. Применяется только для стендовых испытаний.

`currentSteps*` при этом **не обнуляются**: координата остаётся фактической, а `syncPlannerToActual()` приравнивает к ней математическую базу планировщика. Поэтому телеметрия и первый JOG согласованы, «ухода на метры» нет.

### 3.6 Программные лимиты (soft limits)

- `validateMachineTarget(x, y, z, reason)` проверяет точку в машинных координатах по `minX…maxZ`.
- Учитывается лазерная поправка провиса по X (`corr.y_offset`, `corr.z_offset`); WCS и наклон заготовки уже применены вызывающим кодом.
- Допуск — 0,01 мм (округление float/шагов), это не запас рабочей зоны.
- Проверка вызывается перед каждым кадром УП, JOG и точкой скана; `prepareVectorSegment()` повторяет её как защиту от обхода.
- При выходе за лимит: `ERROR: Soft limit X=... outside [...]`, кадр не ставится в очередь, программа останавливается в `IDLE`. Частичного выполнения нет.
- Хоуминг лимитами не ограничивается — он движется к концевикам.

## 4. Генерация шагов и буферизация

### 4.1 Структуры и память

Каждая ячейка времени — 4 байта (7 битовых полей, выравнивание по 32 бита):

```cpp
struct StepCmd {
    uint32_t stepX : 1; // 1 = импульс STEP HIGH
    uint32_t dirX  : 1; // 1 = HIGH
    uint32_t stepY : 1;
    uint32_t dirY  : 1;
    uint32_t stepZ : 1;
    uint32_t dirZ  : 1;
    uint32_t valid : 1;
};
```

- `STEP_BUFFER_SIZE = 4096` → **16 КБ** статической SRAM.
- `BinaryCommand` — `__attribute__((packed))`, **27 байт**: `uint8_t` + `uint16_t` + 6 × `float` (`x, y, z, f, v_start, v_end`).
- `gcodeBuffer` — статический массив **2000 × 27 = 54 КБ** (не «динамическая куча»).
- `curvatureMap` — 250 точек × 8 байт = **2 КБ**.

Итого только под эти структуры — около 72 КБ статической памяти.

### 4.2 Межзадачный обмен

`prepareVectorSegment()` (Core 1, `loop`) заполняет `nextSeg` и взводит `hasNewData` + `isPlannerBusy` + `isVectorMoving`. `motionTask` копирует поля, сразу сбрасывает `hasNewData` (handshake) и генерирует такты. `isPlannerBusy` снимается только когда **и новых данных нет, и кольцевой буфер полностью пуст**.

### 4.3 Планировщик кадра

Для каждого кадра:

1. Пересчёт миллиметров в шаги, вычитание прошлой математической базы `plannerSteps*`.
2. Оптическая поправка провиса по **целевой** X кадра.
3. Разбиение вектора на 3 сегмента: разгон / круиз / торможение (короткий вектор — треугольный профиль без круиза).
4. Целочисленная валидация: `dX[0]+dX[1]+dX[2] == totalDeltaX`; расхождение округления принудительно добавляется в сегмент торможения.
5. Потактовый Брезенхем по ведущей оси; частота считается от `currentVelocity` и `maxSegmentSteps / totalLength_mm`.
6. Запись пустых/рабочих ячеек в кольцо; при заполнении — `vTaskDelay(1)`.

Основные параметры профиля: `v_frame` (подача), `accel = cfg.maxAcceleration`, `v_start`/`v_end` от Look-Ahead ПК. Скорости на стыках рассчитывает **Python-планировщик GUI**, ESP32 их не пересчитывает.

### 4.4 Сейчас: конвейер кадров

> **⚠ Отличие:** следующий кадр запрашивается только при `isPlannerBusy == false`, то есть после **полного опустошения** кольцевого буфера. Между кадрами возникает пауза: станок успевает замереть, а следующий кадр стартует с `v_start`, которая может быть десятки мм/с. Заявленный непрерывный Look-Ahead и «подушка 40 мс» на стыках кадров фактически не работают.

### 4.5 ISR

- Каждый вызов: если `motionStopRequested` — только опустить STEP и выйти; иначе проверка ESTOP/ALARM/концевиков (`digitalRead` × 3), затем одна фаза.
- HIGH: выставить DIR, поднять STEP, инкрементировать `currentSteps*`; LOW: опустить STEP.
- Реальных вычислений с плавающей точкой нет.
- При аварии — `emergencyStopFromISR()`: обесточивание, сброс очереди, флаги. Никаких `changeState()`/`Preferences`/`Serial`/`String`.
- При пустом буфере `isVectorMoving = false`.

### 4.6 HOLD / RESUME / OVERRIDE

- `updateFeedrateFading()` вызывается в `loop()` не чаще раза в 5 мс.
- `OVERRIDE=<0.1…2.0>` плавно меняет `pythonFeedrateOverride`; множитель применяется при **генерации** ячеек (задержка до заполнения буфера).
- При `HOLD` включается `virtualSpeedLimit`, который уменьшается с темпом `cfg.maxAcceleration` (при 10 мм/с — порядка 60–70 мс, а не фиксированные 300 мс). При достижении нуля генератор встаёт в цикл ожидания.
- `RESUME` выводит из ожидания и **не очищает** кольцевой буфер: уже рассчитанные шаги доигрываются, DDA продолжает с текущего индекса, итоговая координата не меняется.
- `HOLD → IDLE/ALARM` теперь останавливает движение: `changeState()` вызывает `requestMotionStop()`, генератор видит флаги, таймер выключается, очередь очищается. «Ползка» на 0,1 мм/с после остановки нет.
- `STOP` — явная мягкая остановка: снять генерацию, очистить очередь, остаться в `IDLE`, сохранить `isHomed`.

### 4.7 Краевые случаи математики

- Если `v_start > v_max` или `v_end > v_max`, длины сегментов становятся отрицательными, доли `pct_*` — отрицательными, и первый сегмент может поехать **в обратную сторону**. Клампов нет.
- При `v_max = 0` (например, F не передан) шаг растягивается до `uint16_t(100000/1) = 34464` ячеек ≈ **344 мс на шаг**.
- `delay100kHz` — `uint16_t`: на частотах ниже ~1,53 Гц происходит переполнение.
- Нижний предел эффективной скорости — 0,1 мм/с; верхний — 1 ячейка на шаг.

## 5. Алгоритмы компенсации

### 5.1 Рабочая система координат (WCS / G54)

- `SET_ZERO:X|Y|Z|ALL` фиксирует текущую машинную позицию как ноль детали и сохраняет смещения в NVS.
- В кадре: `machine = cmd + wcsOffset`, затем (если включён наклон) добавляются поправки Y/Z.
- Телеметрия отдаёт координаты детали: `(currentSteps / stepsPerMm) - wcsOffset`.

### 5.2 Программный разворот заготовки (точки A/B)

- Оператор фиксирует точки A и B (`SET_ALIGN_A/B`), затем `ACTIVATE_ALIGN`.
- При `|ΔX| ≥ 10 мм` считаются `slopeY = ΔY/ΔX`, `slopeZ = ΔZ/ΔX`; значения и флаг сохраняются в NVS.
- При активном наклоне для G0/G1: `Y += (machineX - A.x) * slopeY`, `Z += (machineX - A.x) * slopeZ`.
- `DEACTIVATE_ALIGN` выключает коррекцию и сохраняет флаг.

> **⚠** Коррекция применяется только к кадрам УП. JOG, `SCAN_GEOMETRY` и `START_CALIBRATION` её не используют (вопреки прежнему описанию).

### 5.3 Оптическая карта провиса фермы

- Таблица `curvatureMap[250]`; по умолчанию `laserMapSize = 201`, `laserGridStep = 20 мм` → зона 0…4000 мм.
- Линейная интерполяция между соседними точками; X ограничивается `[0, (size-1)*gridStep]`.
- Поправка Y/Z берётся по **конечной** X кадра и применяется ко всему кадру (на длинных G0 это ступенька на стыке).
- Источники карты: `MAP_LOAD:IDX=…;Y=…;Z=…` с ПК или `START_CALIBRATION` (сейчас без движения).
- `updateLaserMapCommunication()` читает `Serial2`, разбирает `OFFSET: Y=…; Z=…`, но **никуда не сохраняет** — живой контур ESP32-CAM не влияет на движение.

> **⚠** `updateCurvaturePoint()` проверяет только `index < cfg.laserMapSize`, но не верхнюю границу массива 250. `SET_CONFIG:laserMapSize=…` может вывести запись/чтение за пределы `curvatureMap`.
> **⚠** `START_CALIBRATION` не позиционирует каретку: цикл замеров выполняется в одной точке.
> **TODO:** валидация `1 ≤ laserMapSize ≤ 250`, `laserGridStep > 0`, непрерывная интерполяция внутри кадра, приём и применение данных CAM.

### 5.4 Комплексное сканирование геометрии

`SCAN_GEOMETRY:<START>;<END>;<STEP>;<SPEED>`:

1. `stepsCount = |END - START| / STEP + 1` (валидации `STEP ≠ 0` нет).
2. Каретка едет в `prepareVectorSegment(currentX, 0, 0, SPEED, …)` — **машинные** координаты, без WCS/наклона; поверх Y/Z всё равно накладывается лазерная поправка, если карта непустая.
3. Ожидание `isPlannerBusy`, пауза **600 мс** на гашение вибраций фермы.
4. Замер щупа (`readDialIndicator`, до 50 мс) и запрос к ESP32-CAM (`MEASURE`, таймаут 1500 мс).
5. Выдача CSV в `Serial` и Wi-Fi: `X;DIAL_INDICATOR;LASER_Y;LASER_Z` (без префикса).

> **⚠** GUI ожидает строки `SCAN:<x>;<z>;<type>` — форматы не совпадают.
> **⚠** Процедура блокирует `loop()` на всё время скана: телеметрия и Wi-Fi-команды (включая `ESTOP`) не обрабатываются; доступна только аппаратная авария, проверяемая вручную.

### 5.5 Цифровой индикатор (24-битный протокол)

- `INDICATOR_CLK = GPIO18`, `INDICATOR_DATA = GPIO19`, `INPUT_PULLUP`.
- Ожидание старта (CLK LOW) — таймаут 50 мс; далее 24 бита по спаду CLK, таймауты 1 мс на фронт.
- Бит с индексом 20 — знак; биты 0…19 — величина; результат `value * sign / 100.0` мм.
- При обрыве/таймауте — `-999.0` (в CSV выводится `DISCONNECTED`).

## 6. Сетевой протокол (TCP, порт 8888)

### 6.1 Транспорт

- ESP32 поднимает точку доступа `CNC_4METERS_ROUTER` / `CNC_password_123` (пароль зашит в `wifi_manager.cpp`; **сменить перед эксплуатацией**).
- TCP-сервер слушает **8888**, одновременно обслуживается один клиент.
- Команды и ответы — строки, разделитель `\n` (парсер также принимает `\r`).
- Тот же диспетчер команд используется для USB-UART `Serial` (115200), поэтому USB и Wi-Fi равноправны.

### 6.2 Телеметрия

Каждые `statusInterval` мс (по умолчанию **1000**) в Wi-Fi и USB уходит:

```text
<Status:IDLE (LOCKED)|Pos:X=0.00,Y=0.00,Z=0.00|Hom:0|Line=0>
```

- `<Status:…>` — имя состояния; суффикс ` (LOCKED)` добавляется только для `INIT`/`IDLE` при `!isHomed`.
- `Pos` — координаты **детали** (WCS), 2 знака.
- `Hom` — 1/0.
- `Line` — номер текущего кадра (`uint16_t`).
- При `sendOnlyOnChange = false` строка отправляется каждый интервал; при `true` — только при изменении.
- **⚠** `sendToWiFiClient()` дополнительно печатает всё в `Serial`, а `reportStatusToPC()` печатает статус ещё раз → в USB каждая строка статуса дублируется.
- Дополнительные строки: `SINGLE_BLOCK_WAIT` (при покадровом режиме), CSV сканера, `DATA: Point …`, `LAST_LINE:N`, `CONFIG_DATA:…`.

### 6.3 Глобальные команды (доступны в любом состоянии)

| Команда | Действие |
|---|---|
| `ESTOP` | `STATE_ALARM`, моторы обесточены, реле выключены |
| `STOP` | мягкая остановка: очистка очереди, `IDLE`, `isHomed` сохраняется; в `ALARM` остаётся `ALARM` |
| `RESET_ALARM` | `isHomed = false`, остановка движения, переход в `IDLE` (машина снова LOCKED) |
| `HOLD` или `!` | пауза из `RUNNING`/`JOGGING` |
| `RESUME` или `~` | продолжение из `HOLD` без потери шагов |
| `OVERRIDE=<0.1…2.0>` | плавный множитель подачи |

> `RESET_ALARM`, `STOP` и переход в `ALARM` вызывают `requestMotionStop()`: выдача шагов прекращается сразу, буфер очищается в критической секции. Таймер остаётся работоспособным, поэтому `ESTOP`/`MOTORS_ALARM` по-прежнему обрабатываются в ISR без участия `loop()`.

### 6.4 Команды режима IDLE

| Команда | Действие |
|---|---|
| `HOME` / `$H` | полный цикл хоуминга Z→X→Y |
| `JOG:<G0/G1 … F…>` | ручное перемещение, `F` — мм/мин (см. 6.8) |
| `SET_HOMED_DEBUG` | обнулить счётчики и снять блокировку без хоуминга |
| `SET_ZERO:X|Y|Z|ALL` | обнулить WCS, сохранить в NVS |
| `GET_CONFIG` | выдать `CONFIG_DATA:…` (все поля `CONFIG_FIELDS`) |
| `SET_CONFIG:<name>=<value>` | изменить параметр и сохранить **весь** конфиг в NVS |
| `START_PROGRAM` | старт загруженной УП |
| `START_FROM_LINE:<N>` | старт с строки (фактически всегда с 0) |
| `GET_LAST_ABORTED_LINE` | `LAST_LINE:<N>` (значение сохраняется только в `ALARM`) |
| `SINGLE_BLOCK_ON/OFF` | включить/выключить покадровый режим |
| `SET_ALIGN_A` / `SET_ALIGN_B` | запомнить точки A/B |
| `ACTIVATE_ALIGN` / `DEACTIVATE_ALIGN` | включить/выключить наклон |
| `GCODE_UPLOAD_START` | очистить буфер и перейти в приём УП |
| `START_CALIBRATION` | прогон лазерной карты (сейчас без движения) |
| `EXPORT_MAP` | выгрузка карты CSV в сокет |
| `MAP_LOAD_START` | переход в режим импорта карты |
| `SCAN_GEOMETRY:<START>;<END>;<STEP>;<SPEED>` | скан геометрии, `SPEED` — мм/мин |

> Команды, которые могут начать движение (`START_PROGRAM`, `START_FROM_LINE`, `JOG`, `SCAN_GEOMETRY`, `HOME`, `START_CALIBRATION`), сначала вызывают `changeState()`. Если переход запрещён (`ALARM` или `!isHomed`), в сокет уходит `ERROR: ...`, и движение не начинается. Исключение — `JOG` при `allowJogBeforeHoming = true` (по умолчанию).

### 6.5 Загрузка УП

- `GCODE_UPLOAD_START` → ответ `STATUS: Ready`.
- Далее пакеты:

```text
B:<TYPE>;<LINE>;<X>;<Y>;<Z>;<F>;<V_START>;<V_END>
```

| Поле | Тип | Смысл |
|---|---|---|
| `TYPE` | int | 0/1 — движение (G0/G1), 3/5 — шпиндель, 8/9 — СОЖ |
| `LINE` | int | номер строки исходного файла (`uint16_t`) |
| `X`,`Y`,`Z` | float | целевые координаты **WCS**, мм |
| `F` | float | подача кадра, **мм/с** |
| `V_START`,`V_END` | float | скорости стыка от Look-Ahead, **мм/с** |

- `GCODE_UPLOAD_END` → `STATUS: Upload complete. Loaded N commands.` + `ok`, возврат в `IDLE`.
- При переполнении (2000 кадров) — `ERROR: Add to RAM buffer failed`.

### 6.6 Импорт карты лазера

`MAP_LOAD_START` → серия строк:

```text
MAP_LOAD:IDX=<i>;Y=<offset>;Z=<offset>
```

→ `MAP_LOAD_END` → `IDLE`.

### 6.7 Конфигурация

- `GET_CONFIG` возвращает `CONFIG_DATA:` + `поле=значение;` для **всех** полей `CONFIG_FIELDS` (имена — как в коде, не ключи EEPROM).
- `SET_CONFIG:<name>=<value>` принимает любое поле, сохраняет весь конфиг в NVS и отвечает `STATUS: Config parameter <name> updated and saved.`
- **⚠** Значения `float` в `GET_CONFIG` печатаются с **2 знаками** (`String(float)`), поэтому малые величины (например, `slopeY`) теряют точность.
- **⚠** Валидации нет: можно задать `stepsPerMmX = 0`, `laserMapSize > 250`, отрицательный `laserGridStep` и т.п.

Полный список параметров — раздел 10.

### 6.8 Единицы измерения (фактически)

| Где | Единица | Комментарий |
|---|---|---|
| `B:…;F;…` | **мм/с** | GUI переводит F из мм/мин: `curr_f / 60` |
| `B:…;V_START;V_END` | **мм/с** | результат Look-Ahead GUI |
| `maxAcceleration` | мм/с² | |
| `JOG:…F…` | **мм/мин** | как в G-коде; прошивка переводит в мм/с. Допустимо 1…20000 |
| `SCAN_GEOMETRY:…;SPEED` | **мм/мин** | прошивка переводит в мм/с. Допустимо 1…20000 |
| `defaultFeedRate` | мм/мин | fallback JOG, переводится в мм/с |
| `pullOffX/Y/Z` | шаги | |
| координаты в протоколе | мм | |

### 6.9 Ответы

- `ok` — команда принята/выполнена.
- `ERROR: Unknown or blocked command: …` — команда не разрешена в текущем состоянии.
- `ERROR: Machine is LOCKED. Run HOMING first.` — нарушена блокировка хоуминга.
- `STATUS: …` — текстовые статусы (многие команды выдают `STATUS` и затем `ok`).
- `ERROR: Add to RAM buffer failed`, `ERROR: Look-Ahead binary packet corrupt! …`.

## 11. Известные ограничения и TODO

### 11.1 Блокирующие/критические

1. **Порт на core 3.x не сделан:** проект зафиксирован на Arduino 2.0.17 (`espressif32@6.12.0`); при обновлении платформы потребуется новый API таймера.
2. **Частота 100 кГц:** подачи и ускорения ≈ 50 % расчётных. Вернуть 200 кГц и проверить загрузку CPU/минимальную ширину STEP/потери шагов.
3. **Одно ядро:** `loop`, `motionTask`, ISR — на Core 1; вынести супервизор на Core 0.
4. **Нет потокового конвейера:** следующий кадр только после полного слива буфера → остановки и удары на стыках.
5. **Одна цепь концевиков:** все оси на GPIO 39; при уже открытой цепи хоуминг следующей оси может завершиться сразу (таймаут и контроль хода уже есть — P0-5).
6. **`START_FROM_LINE`** сбрасывает индекс на 0.
7. **Single Block:** нет `NEXT_BLOCK`; `SINGLE_BLOCK_OFF` не проходит в `RUNNING` → программа стоит.
8. **JOG** после успешного перемещения остаётся в `STATE_JOGGING`: следующие `JOG`/`HOME`/`START_PROGRAM` блокируются; выйти можно только через `STOP`/`RESET_ALARM`/`ESTOP`.
9. **Лазерная калибровка** не двигает каретку; `updateLaserMapCommunication()` отбрасывает данные CAM.

### 11.2 Высокие

10. **Клампы скоростей:** `v_start/v_end > v_max` → отрицательные доли сегментов и движение назад внутри кадра; `v_max = 0` → 344 мс/шаг; переполнение `uint16_t delay100kHz`.
11. **Карта провиса:** нет проверки `≤ 250`; коррекция по конечной X кадра; `START_CALIBRATION` без движения; живой CAM не применяется.
12. **Блокирующие сканы:** `loop` недоступен на всё время процедуры; Wi-Fi `ESTOP` не работает. Базовые проверки `STEP/SPEED/START/END` и soft limits уже есть.
13. **Буферы строк** (`wifiInputBuffer`, `inputBuffer`, `camBuffer`) без ограничения длины; Wi-Fi-парсер обрабатывает неполную строку при `available() == 0` → рвёт пакеты.
14. **Буфер УП:** 2000 × 27 байт (проект — 10 000 × 15); `lineNum` — `uint16_t` (предел 65 535 строк).
15. **Шпиндель:** ШИМ отсутствует, только реле; `pwmFrequency`, `pwmResolutionBits`, `feedMultiplier`, `rapidFeedRate` не используются.
16. **`GET_CONFIG`** округляет float до 2 знаков; `SET_CONFIG` без валидации.
17. **Аппаратные мелочи:** `INPUT_PULLUP` на GPIO 34/35/39 не действует; на модуле с PSRAM GPIO 16/17 заняты.
18. **Расхождения с GUI:** формат скана, отображение суффикса `(LOCKED)` в статусе, отсутствие flow control и проверки лимита при заливке.

### 11.3 Низкие

19. Дублирование телеметрии в USB.
20. `G01` парсится как `G0` (поиск подстроки `G0`).
21. Нет тестов и CI; математику планировщика стоит вынести в `native`-тесты PlatformIO.
22. **M-коды** обрабатываются рекурсивным вызовом `executeNextProgramStep()`: длинная серия `M3/M5/M8/M9` подряд может переполнить стек.
23. `STATE_GCODE_UPLOAD` и `STATE_MAP_TRANSFER` отсутствовали в старом описании FSM.
24. Устаревшие комментарии: в `gcode_program.h` структура названа «13 байт» (фактически 27), в `motion.cpp` ISR описан как «200 кГц» и «Core 0».
