# 4. Генерация шагов и буферизация

> Часть паспорта прошивки. Оглавление — [INDEX.md](INDEX.md).
> **Читать перед:** правками планировщика, `motionTask`, ISR, кольцевого буфера, HOLD/OVERRIDE.
> **Источник истины:** `src/motion.cpp`, `src/motion.h`.

## 4.1 Структуры и память

Каждая ячейка времени — 4 байта (7 битовых полей, выравнивание по 32 бита):

```cpp
struct StepCmd {
    uint32_t stepX : 1; // 1 = импульс STEP HIGH
    uint32_t dirX  : 1; // 1 = HIGH
    uint32_t stepY : 1;
    uint32_t dirY  : 1;
    uint32_t stepZ : 1;
    uint32_t dirZ  : 1;
    uint32_t valid : 1;
};
```

- `STEP_BUFFER_SIZE = 4096` → **16 КБ** статической SRAM.
- `BinaryCommand` — `__attribute__((packed))`, **27 байт**: `uint8_t` + `uint16_t` + 6 × `float` (`x, y, z, f, v_start, v_end`).
- `gcodeBuffer` — статический массив **2000 × 27 = 54 КБ** (не «динамическая куча»).
- `curvatureMap` — 250 точек × 8 байт = **2 КБ**.

Итого только под эти структуры — около 72 КБ статической памяти.

## 4.2 Межзадачный обмен (очередь кадров, P1-3)

Core 0 складывает готовые кадры в межъядерную очередь `frameQueue` глубиной
`FRAME_QUEUE_SIZE = 4` слота. Всё под `xferMux`: индексы и счётчик меняются в
одной критической секции, поэтому отдельного флага-отмашки (`hasNewData`) нет —
недописанный кадр другое ядро не увидит.

- `prepareVectorSegment()` (Core 0, `supervisorTask`) публикует кадр в свободный
  слот и сразу возвращает `true`. Ждёт только когда очередь полна: это значит,
  что кольцо тактов забито и Core 1 идёт вровень с реальным временем.
- `motionTask` (Core 1) забирает кадр из хвоста, взводит `isMotionGenerating` и
  генерирует такты.
- `canQueueFrame()` — «есть свободный слот»: по нему `supervisorTask` держит
  конвейер заполненным, не дожидаясь слива предыдущего кадра.
- `isPlannerBusy` снимается только когда **и очередь, и кольцо пусты**. Это и есть
  «станок стоит, шагов больше не будет» — по нему завершается программа,
  синхронизируется JOG и ждут сканы.

## 4.3 Планировщик кадра

Для каждого кадра:

1. Пересчёт миллиметров в шаги, вычитание прошлой математической базы `plannerSteps*`.
2. Оптическая поправка провиса по **целевой** X кадра.
3. Разбиение вектора на 3 сегмента: разгон / круиз / торможение (короткий вектор — треугольный профиль без круиза).
4. Целочисленная валидация: `dX[0]+dX[1]+dX[2] == totalDeltaX`; расхождение округления принудительно добавляется в сегмент торможения.
5. Потактовый Брезенхем по ведущей оси; частота считается от `currentVelocity`, зажатой сверху `virtualSpeedLimit` (пауза), и от `maxSegmentSteps / totalLength_mm`.
6. Запись пустых/рабочих ячеек в кольцо; при заполнении — `vTaskDelay(1)`.

Основные параметры профиля: `v_frame` (подача), `accel = cfg.maxAcceleration`, `v_start`/`v_end` от Look-Ahead ПК. Скорости на стыках рассчитывает **Python-планировщик GUI**, ESP32 их не пересчитывает.

## 4.4 ФАКТ: конвейер кадров

Очередь из 4 кадров заполняется на Core 0, пока в ней есть свободный слот,
поэтому следующий кадр уже лежит на Core 1 к моменту, когда кольцо тактов
доиграло предыдущий. Паузы на стыке кадров нет: STEP идёт непрерывно, а
скорость стыка задают `v_end` предыдущего и `v_start` следующего кадра.

Что осталось неидеальным:

- `Line` в телеметрии опережает физику на длину очереди (до 4 кадров).
- Непрерывность стыка держится на согласованных `v_end == v_start` соседних кадров от
  GUI. Прошивка зажимает каждую из них в коридор (§4.7), но не сверяет между кадрами:
  рассогласование обернётся рывком на стыке, а не ошибкой.
- Кольцо на 40,96 мс — единственный запас на дрожание планировщика: Core 0 не
  должен задерживать заполнение очереди дольше этого времени.
- **M-коды — барьер конвейера.** `M3/M5/M8/M9` не кладутся в очередь: реле
  срабатывает только после полного слива кольца и очереди, иначе оно щёлкало бы
  за несколько кадров до своей точки траектории.
- **Длинный кадр приходит нарезанным.** Фидер (а для `JOG` — цикл `supervisorTask`)
  режет кадр на куски не длиннее интервала карты провиса, чтобы поправка Y/Z не
  теряла изгибы внутри кадра ([geometry.md §5.3](geometry.md#53-оптическая-карта-провиса-фермы)).
  Куски коллинеарны, углов нет; скорость стыка считается физически достижимой:
  `v_out = min(F, √(v_in² + 2aL), √(v_end² + 2a·R))`, где `L` — длина куска,
  `R` — остаток кадра. Иначе кламп в `prepareVectorSegment()` поднял бы слишком
  низкую скорость и на стыке кусков был бы рывок. `v_start`/`v_end` исходного
  кадра остаются на его краях.

## 4.5 ISR

- Каждый вызов: если `motionStopRequested` — только опустить STEP и выйти; иначе проверка ESTOP/ALARM/концевиков через `safety*Active()` (при `SAFETY_INPUTS_ENABLED=0` это константа `false`, `digitalRead` не вызывается), затем одна фаза.
- HIGH: выставить DIR, поднять STEP, инкрементировать `currentSteps*`; LOW: опустить STEP.
- Реальных вычислений с плавающей точкой нет.
- При аварии — `emergencyStopFromISR()`: обесточивание, сброс очереди, флаги. Никаких `changeState()`/`Preferences`/`Serial`/`String`.
- При пустом буфере `isVectorMoving = false`.

## 4.6 HOLD / RESUME / OVERRIDE

- `updateFeedrateFading()` вызывается в `supervisorTask` на каждом круге, но внутри ограничена периодом 5 мс.
- `OVERRIDE=<0.1…2.0>` плавно меняет `pythonFeedrateOverride`; множитель применяется при **генерации** ячеек (задержка до заполнения буфера).
- `HOLD` запоминает, откуда пришёл (`RUNNING`/`JOGGING`), и `RESUME` возвращает туда же: пауза во время JOG не запускает загруженную УП.
- При `HOLD` включается `virtualSpeedLimit`, который уменьшается с темпом `cfg.maxAcceleration` (при 10 мм/с — порядка 60–70 мс, а не фиксированные 300 мс). Когда лимит упал до нуля, генератор снимает `isMotionGenerating` и **встаёт на границе шага**: DDA не сдвигается, в кольцо ничего не пишется, уже догенерированные ячейки доигрывает ISR.
- Очередь кадров при `HOLD` продолжает заполняться: заморожен только генератор, поэтому `RESUME` не начинается с пустого кольца.
- `RESUME` не очищает ни кольцо, ни очередь: индекс DDA и накопители Брезенхема сохраняются, кадр продолжается с той же точки — итоговая координата от паузы не зависит.
- `HOLD → IDLE/ALARM` (`STOP`, `RESET_ALARM`, E-STOP) останавливает движение: `changeState()` вызывает `requestMotionStop()`, генератор видит флаги и прерывает кадр. `isMotionGenerating` снят ещё на паузе, поэтому остановка не ждёт таймаута 100 мс. «Ползка» на 0,1 мм/с после остановки нет.
- `STOP` — явная мягкая остановка: снять генерацию, очистить очередь, остаться в `IDLE`, сохранить `isHomed`.

## 4.7 Краевые случаи математики

Кадр проверяется до постановки в очередь, в `prepareVectorSegment()`:

- `F <= 0`, `accel <= 0`, любое `NaN/Inf` в пакете — кадр **отклоняется** ошибкой `ERROR: Frame …`, станок не двигается. Раньше `F = 0` упирался в предохранитель 1 Гц и растягивал шаг до 100 000 ячеек = 1 с.
- `v_start`/`v_end` больше подачи кадра — ошибка планировщика GUI: длины сегментов становятся отрицательными, первый сегмент едет назад. Превышение больше 1 % (допуск на округление float) кадр отклоняет, в пределах допуска скорость зажимается. Снизу коридор — `min(minVectorSpeed, F)`: ниже стык рвётся, но поднимать границу выше подачи кадра нельзя, иначе медленный JOG (1 мм/мин = 0,017 мм/с) прыгал бы на 2 мм/с.
- JOG, скан и калибровка передают скорость стыка как `min(minVectorSpeed, F)`: иначе ручной ход со скоростью ниже 120 мм/мин отклонялся бы как `v_start > F`.
- `ticksPerStep` ограничен сверху 100 мс на шаг (`CNC_CELL_HZ / 10`), снизу — 1 ячейкой.
- Нижний предел скорости генерации — 0,1 мм/с (`MIN_FRAME_SPEED_MM_S`); верхний — 1 ячейка на шаг, то есть 100 кГц.
