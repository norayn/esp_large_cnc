> Раздел §7.1. Оглавление — [INDEX.md](INDEX.md).
> **Читать перед:** разработкой или переписыванием GUI; сценарии и приёмка — [gui-flows.md](gui-flows.md) (§7.2).
> **Источник истины:** команды, форматы и единицы — [protocol.md](protocol.md) и `src/`; текущий клиент — [norayn/large_cnc_gui](https://github.com/norayn/large_cnc_gui).
> **Статус:** описание текущего PyQt6-клиента и требований к любому клиенту. Известные расхождения прошивки и GUI — [gui.md](gui.md) (§7).

## Границы ответственности

GUI — операторская панель, а не второй контроллер.

- GUI готовит УП: разбирает G-код, считает Look-Ahead, упаковывает кадры `B:`; показывает координаты, состояние, карту и логи.
- Прошивка — единственный арбитр безопасности: состояние, хоуминг, soft limits, физика кадра, аварийные входы. GUI не дублирует эти проверки как защиту.
- `ERROR: ...` — штатный ответ на недопустимую команду, а не сбой связи. Повторять команду движения автоматически нельзя.
- «Команда выполнена» подтверждает только телеметрия (`IDLE`, `Hom`, `Line`) или явный `STATUS`; `ok` на `JOG` означает лишь приём команды.

## Репозиторий и карта модулей

| Модуль | Ответственность |
|---|---|
| `main.py` | сборка окна, сигналы, единая точка отправки команд, лог сессии |
| `connection_worker.py` | `QThread`: TCP/USB, чтение строк, первичный разбор телеметрии и скана |
| `machine_state.py` | единый источник истины: координаты, статус, `Hom`, `Line`, конфиг |
| `gcode/core_planner.py` | парсер G-кода, Look-Ahead, упаковка `B:` |
| `gcode_planner_oo.py` | старая копия планировщика, не использовать |
| `gui/main_window.py` | DRO, вкладки, лента УП, 3D, MDI, статус-бар |
| `gui/tabs/tab_*.py` | вкладки JOG, файлы, выравнивание, диагностика |
| `gui/dialog_settings.py` | таблица `CONFIG_FIELDS`, `SET_CONFIG` по изменённым полям |
| `gui/dialog_log.py` | терминал и фильтрация телеметрии |
| `gui/static_control.py`, `visualizer_3d.py`, `gcode_list.py` | DRO, 3D, лента кадров |

Запуск: `pip install -r requirements.txt`, затем `python main.py`. Сейчас `main.py` при старте жёстко открывает USB `COM4`; для эксплуатации нужен диалог выбора Wi-Fi/USB и порта.

## Потоки, состояние, команды

- `CNCConnectionWorker` — `QThread`; `run()` читает сокет/порт и шлёт сигналы `telemetry_received`, `scan_point_received`, `log_received`, `connection_status`.
- `CNCMachineState` — единственный источник состояния для UI; обновляется только из разобранных входящих строк. Виджеты не хранят свои копии координат и статуса.
- Команды: виджеты испускают `command_requested(str)`, `main.py` пишет строку в лог и передаёт транспорту. Виджет не обращается к сокету напрямую.
- Сейчас `send_command()` вызывается из GUI-потока, пока worker читает в своём; сокет это терпит, последовательный порт — хуже. В переписывании нужна исходящая очередь и один писатель внутри worker.
- Переподключение: остановить worker, дождаться завершения, закрыть соединение, сбросить состояние в `DISCONNECTED`, поднять новый worker, затем `GET_CONFIG`. Старый конфиг после обрыва не переиспользовать.

## Подключение и транспорт

- Wi-Fi: TCP-клиент `192.168.4.1:8888`, прошивка обслуживает один клиент; команды и ответы — строки ([protocol.md §6.1](protocol.md#61-транспорт)).
- USB: serial 115200, тот же диспетчер команд. Открытие порта может перезагрузить ESP32 по DTR/RTS: подождать ~1,5 с и слить вход.
- Отправка: ASCII, одна команда на строку, `\n` (текущий клиент шлёт `\r\n`; прошивка принимает оба).
- Приём: накапливать байты, делить по `\n`, срезать `\r` и пробелы. Одно чтение может содержать несколько строк, а строка — прийти кусками.
- Телеметрия чередуется с ответами. У ответов нет идентификатора запроса: либо сериализовать запрос/ответ, либо считать `ok`/`ERROR` событиями потока.
- При `sendOnlyOnChange=true` одинаковая телеметрия не приходит: тишина ≠ обрыв. Обрыв определять по состоянию сокета/ошибке чтения.
- Автопереподключение во время движения или заливки запрещено.

## Разбор входящих строк

| Вид строки | Что это | Куда |
|---|---|---|
| `<Status:...>` | телеметрия, [§6.2](protocol.md#62-телеметрия) | состояние, DRO, лента |
| `CONFIG_DATA:` | все поля конфига, [§6.7](protocol.md#67-конфигурация) | `machine_state.config` |
| `ok`, `ERROR: ...` | ответ на команду, [§6.9](protocol.md#69-ответы) | лог, флаги ошибок |
| `STATUS: ...` | текстовый статус | лог, уведомление |
| `LAST_LINE:N` | последний кадр при аварии | предложение продолжить |
| `=== START/END ... ===` | границы скана/карты | прогресс, диалог |
| `DATA: Point ...` | результат калибровки карты | таблица, график |
| `<X>;<DIAL>;<LASER_Y>;<LASER_Z>` | скан геометрии, [§5.4](geometry.md#54-комплексное-сканирование-геометрии) | график |
| `MAP_LOAD:`, CSV карты | импорт/экспорт карты, [§6.6](protocol.md#66-импорт-карты-лазера) | карта |

- `Status:IDLE (LOCKED)`: базовое состояние — токен до первого пробела; `(LOCKED)` означает `!isHomed` для `INIT`/`IDLE`. Сравнивать всю строку с `"IDLE"` нельзя.
- Скан геометрии идёт **без** префикса `SCAN:`; `DIAL`/`LASER_Y`/`LASER_Z` могут быть `DISCONNECTED`. Текущий клиент ждёт `SCAN:...` и теряет эти строки (P2-7).
- `STATUS: Upload complete...` и `ok` после `GCODE_UPLOAD_END` приходят двумя строками.
- Неизвестные строки сохранять в сырой лог без изменений: это единственный способ увидеть расхождение протоколов.

## Единицы и координаты

| Величина | В GUI | В протоколе |
|---|---|---|
| `F`, `V_START`, `V_END` в `B:` | планировщик считает в мм/с | мм/с |
| `F` в `JOG` | слайдер мм/мин | мм/мин |
| `SPEED` в `SCAN_GEOMETRY` | мм/мин | мм/мин |
| `defaultFeedRate` | мм/мин | мм/мин |
| координаты | мм | мм |

- Телеметрия `Pos` — **WCS** (деталь). `MCS = WCS + wcsOffsetX/Y/Z` из конфига; наклон A/B в это равенство не входит — прошивка применяет его к кадрам УП ([§5.2](geometry.md#52-программный-разворот-заготовки-точки-ab)).
- После `SET_ZERO:*` и смены офсетов/наклона перезапросить `GET_CONFIG`, иначе MCS в GUI останется старым.
- `Line` — номер последнего кадра, **поставленного в конвейер**, а не физически выполненного: опережает до 4 кадров. Подсветка ленты и прогресс приблизительные ([§6.2](protocol.md#62-телеметрия)).
- `Hom` — единственный признак готовности к `START_PROGRAM`; без хоуминга координаты могут быть произвольными.

## Рекомендации к переписыванию

- Разделить слои: транспорт (reader/writer + очередь), кодек протокола, планировщик, хранилище состояния, UI. Виджеты не знают строк протокола.
- Один писатель в сокет/порт, один reader-поток; все команды — через очередь с временем и логом.
- Кодек и планировщик покрыть тестами на золотых пакетах: `B:`-строка, телеметрия с `(LOCKED)`, `CONFIG_DATA`, CSV скана, `MAP_LOAD`.
- Ввести версию протокола (`PROTO:1`) — ПЛАН P2-7; до неё фиксировать совместимость этим документом.
