## P2 — команды, протокол, парсеры, конфиг, шпиндель

- **P2-1 · Исправить `START_FROM_LINE`.** *(2026-11-18: `startProgramExecution(startIndex)` запускает с найденного кадра, первый кадр движения входит с нулевой скоростью; коммит `35d0a51`)*
  `src/wifi_manager.cpp` — `handleIdleCommands()`; `src/gcode_program.cpp/.h` — `startProgramExecution()`.
  Обработчик находил индекс строки, но `startProgramExecution()` безусловно ставил `currentCommandIndex = 0`, поэтому УП всегда шла с начала. Если строки в буфере не было, обработчик молча завершался, не сообщая об ошибке.
  **Сделано:** стартовый индекс передаётся параметром (`int startIndex = 0`) и проверяется на диапазон; `currentCommandIndex` выставляется на найденный кадр, `syncPlannerToActual()` по-прежнему привязывает планировщик к фактической позиции, `resetSplit()` убирает недоигранную нарезку. Неизвестная строка — `ERROR: Line <N> not found in loaded program.` в TCP и USB. При `startIndex > 0` у первого кадра движения обнуляется `v_start`: Look-Ahead считал вход из кадра, которого в этом запуске нет, а станок стоит.
  **Как проверено:** `pio run` — SUCCESS; запуск с середины файла на железе не прогонялся (нет доступа к станку).

- **P2-8 · Убрать рекурсию M-кодов.** *(2026-11-18: закрыт ещё в P1-3 — `executeNextProgramStep()` не вызывает себя; коммит `7b3b8df`)*
  `src/gcode_program.cpp` — `executeNextProgramStep()`; `src/main.cpp` — цикл `supervisorTask`.
  Каждый M-код вызывал `executeNextProgramStep()` рекурсивно, и длинная серия `M3/M5/M8/M9` могла переполнить стек `supervisorTask`.
  **Сделано (P1-3):** M-код — барьер конвейера: он исполняется только после слива кольца и очереди, индекс сдвигается, функция возвращает `true`, а следующий кадр забирает цикл `while (canQueueFrame() && executeNextProgramStep())` в `supervisorTask`. Рекурсивных вызовов в коде нет, глубина стека не зависит от числа M-кодов.
  **Проверено:** поиск по `executeNextProgramStep()` даёт только объявление, начальный вызов в `startProgramExecution()` и цикл фидера; `pio run` — SUCCESS; серия 2000 M-кодов на железе не прогонялась.

- **P2-9 · Исправить разбор `G01`.** *(2026-11-18: `parseGWord()` читает номер G-слова как число; `G01`/`G1.0` — это `G1`, `G10` отклоняется; коммит `9ee3e7a`)*
  `src/gcode_program.cpp` — `processSingleManualCommand()`, `parseGWord()`.
  `line.indexOf("G0")` срабатывал внутри `G01`, поэтому тип оставался 0 (G0) вместо G1; `indexOf("G1")` так же ловил `G10`.
  **Сделано:** номер G-слова ищется как отдельный токен `G<цифры>` на границе слова, дробная часть отбрасывается (номера G-кодов целые). `G0`/`G00` → G0, `G1`/`G01`/`G1.0` → G1, остальные номера отклоняются прежней проверкой `ERROR: JOG requires G0 or G1.` Регистр не важен: строка приводится к верхнему до разбора.
  **Как проверено:** `pio run` — SUCCESS; разбор прогнан на наборе строк (`G0`, `G00`, `G1`, `G01`, `G1.0`, `g1`, `G1X10`, `G10`) отдельным стендом; на железе JOG не прогонялся.

- **P2-3 · Возвращать JOG в `IDLE`.** *(2026-11-17: `supervisorTask` снимает `JOGGING` по `!isSplitActive() && !isPlannerBusy`, новый JOG — только из `IDLE`; коммит `5c222d3`)*
  `src/main.cpp` — цикл `supervisorTask`; `src/wifi_manager.cpp` — `handleIdleCommands()`; `docs/fsm-safety.md §3.2`.
  После JOG станок оставался в `STATE_JOGGING` навсегда: `handleIdleCommands()` работает только в `IDLE`, поэтому следующие `JOG`/`HOME`/`START_PROGRAM` отклонялись, и выйти можно было только через `RESET_ALARM`/`ESTOP`.
  **Сделано:** когда нарезка закончена и `isPlannerBusy = false` («очередь кадров и кольцо шагов пусты»), `supervisorTask` переводит FSM в `IDLE`. Это условие «станок стоит», поэтому переход не режет остаток хода и не зависит от времени: таймаут не нужен, а зависание движения — отдельная диагностика. Новый JOG принимается только в `IDLE` (очередь JOG не поддерживается намеренно: второй JOG во время нарезки сбросил бы остаток первого), серия команд идёт по факту `IDLE` в телеметрии.
  **Как проверено:** `pio run` — SUCCESS; серия JOG на железе не прогонялась (нет доступа к станку).

- **P2-6 · Убрать дублирование телеметрии.** *(2026-11-17: `sendToWiFiClient()` — только TCP, добавлен `sendToBothClients()` для TCP+USB; период телеметрии ограничен снизу 50 мс; коммит `d936b08`)*
  `src/wifi_manager.cpp/.h` — `sendToWiFiClient()`, `sendToBothClients()`; `src/state_manager.cpp` — `reportStatusToPC()`; `src/main.cpp`; `docs/protocol.md §6.2`.
  `sendToWiFiClient()` печатала строку и в сокет, и в `Serial`, а `reportStatusToPC()` печатал статус в `Serial` ещё раз → в мониторе USB каждая строка телеметрии шла дважды. Тот же эхо-дубль был у всех пар `Serial.println(err); sendToWiFiClient(err);`.
  **Сделано:** у каждого канала один владелец вывода. `sendToWiFiClient()` — только TCP; `sendToBothClients()` — ровно одна строка в TCP и одна в USB; через него идут телеметрия и ответы на команды. Пары `Serial.println` + `sendToWiFiClient` теперь дают по одной строке в каждый порт. Период `statusInterval` ограничен снизу 50 мс: без этого `0`/отрицательное значение из `SET_CONFIG` слало бы телеметрию каждый круг `supervisorTask`.
  **Как проверено:** `pio run` — SUCCESS; одна строка статуса на интервал в USB-мониторе не проверялась — нет доступа к станку.
